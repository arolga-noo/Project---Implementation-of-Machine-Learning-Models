## Архитектура сервиса: 
В рамках данного учебного проекта для развертывания скорингового веб-сервиса был выбран модульный монолитный подход (пакет кода, веса модели и API-интерфейс упакованы в один Docker-контейнер). Этот выбор обусловлен следующими инженерными факторами:
- Минимизация сетевых задержек: в кредитном скоринге скорость принятия решения по заявке критична. В монолитной архитектуре инференс (обработка данных моделью LogisticRegression) происходит внутри одного процесса в оперативной памяти. Это исключает накладные расходы на сетевое взаимодействие (Network Overhead), неизбежные при межсервисном общении в микросервисной архитектуре.
- Упрощение деплоя и оркестрации: на этапе построения MVP (минимально жизнеспособного продукта) монолит избавляет от необходимости разворачивать сложные сервисы Service Discovery, распределенные базы данных и оркестраторы вроде Kubernetes. Весь контур стабильно поднимается с помощью базового Docker Compose.
- Простота масштабирования:монолитная архитектура не препятствует масштабированию. При росте нагрузки сервис отлично масштабируется горизонтально — путем запуска нескольких идентичных копий одного и того же Docker-образа за балансировщиком нагрузки NGINX.
- Изоляция доменной логики: код структурирован модульно (выделен отдельный `model_handler.py`), что при необходимости позволит беспрепятственно распределить монолит на микросервисы в будущем, если скоринг станет частью более крупной банковской экосистемы.

## Концепт брокеров сообщений (Масштабирование через RabbitMQ):
В синхронной REST API архитектуре (клиент отправил запрос — сервер заставил клиента ждать ответа) система уязвима для перегрузок при пакетной обработке (Batch Processing). В гипотетическом сценарии масштабирования сервиса на всю базу клиентов банка (например, ежедневный пересчет кредитных лимитов для 1 000 000 пользователей) синхронный подход приведет к падению сервера Flask или превышению таймаута соединения (Gateway Timeout).
Для решения этой задачи в production-системах внедряется брокер очередей сообщений, например RabbitMQ, переводящий сервис на асинхронную событийно-ориентированную архитектуру (EDA).

Сценарий применения RabbitMQ для асинхронного батч-скоринга:

1.  Подача задачи: основной банковский бэкенд формирует реестр из миллиона клиентов и отправляет их идентификаторы и признаки не напрямую в Flask API, а публикует в виде сообщений в очередь `credit_scoring_queue` брокера RabbitMQ. Это занимает секунды, и бэкенд сразу освобождается для других задач.
2.  Пул воркеров (Workers): ML-сервис переводится из режима веб-сервера в режим независимого слушателя очереди (Consumer). В облаке запускается множество параллельных Docker-контейнеров (воркеров) с моделью логистической регрессии.
3.  Асинхронный инференс: каждый воркер порциями (батчами) забирает сообщения из RabbitMQ, выполняет предсказание вероятности дефолта и записывает результаты напрямую в аналитическую базу данных (например, PostgreSQL или ClickHouse).
4.  Отказоустойчивость: если один из контейнеров упадет из-за нехватки памяти, RabbitMQ не потеряет данные. Брокер зафиксирует отсутствие подтверждения (‘ACK’) от упавшего воркера и автоматически перенаправит эти сообщения на другой активный контейнер.

## Логирование и мониторинг (Промышленный контур ELK-стека)
### Формат и место логирования
Для обеспечения наблюдаемости (Observability) системы каждый запрос к эндпоинту `/predict` и результаты инференса логируются в стандартизированном структурированном формате JSON. Логи пишутся напрямую в стандартный поток вывода (`stdout`), что является стандартом для контейнеризированных приложений (согласно методологии Twelve-Factor App).

Пример JSON-лога, генерируемого кодом приложения при каждом запросе:
json
{
  "timestamp": "2026-06-13T11:40:22Z",
  "environment": "production_like",
  "latency_ms": 12.45,
  "batch_size": 1,
  "api_endpoint": "/predict",
  "model_version": "v1.0"
}
### Сбор логов в Production-системе (Стек ELK / EFK)
В реальной промышленной эксплуатации не читаются логи вручную из консоли Docker. Для автоматизированного сбора, агрегации и визуализации настраивается стек ELK (Elasticsearch, Logstash, Kibana):
- Filebeat (Агент сбора): легковесный демон, развернутый на сервере приложений, непрерывно следит за файлами логов Docker-контейнеров, считывает новые строки JSON и мгновенно отправляет их дальше по контуру.
- Logstash (Парсинг и фильтрация): принимает сырые потоки данных от Filebeat, проверяет валидность JSON-структуры, при необходимости обогащает логи метаданными (например, ID сервера или географическим регионом запроса).
- Elasticsearch (Хранение и поиск): высокомасштабируемая база данных, которая индексирует поступающие JSON-логи, обеспечивая мгновенный полнотекстовый поиск по любым полям (например, можно за миллисекунды найти все логи, где время отклика `latency_ms` превысило 100 мс).
- Kibana (Визуализация и дашборды): графический веб-интерфейс, подключенный к Elasticsearch. На основе полей из JSON-логов аналитики и инженеры строят дашборды в реальном времени.

### Назначение мониторинга логов для ML:
 - Контроль технических метрик (SRE): мониторинг среднего времени отклика (Latency), количества входящих запросов (RPS) и процента ошибок HTTP.
- Отслеживание Data Drift (Сдвига данных): на основе логируемых признаков клиентов в Kibana строятся графики распределений. Если распределение входящих признаков начинает резко отличаться от обучающей выборки, система сигнализирует о необходимости переобучения модели.
