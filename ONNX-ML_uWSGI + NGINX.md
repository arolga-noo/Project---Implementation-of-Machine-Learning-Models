# Оптимизация инференса: Конвертация модели в формат ONNX-ML.
ONNX (Open Neural Network Exchange) — это открытый кроссплатформенный стандарт для представления моделей машинного обучения. Формат ONNX-ML расширяет базовый стандарт ONNX, добавляя поддержку классических ML-алгоритмов (таких как логистическая регрессия, деревья решений и SVM), встроенных в библиотеку scikit-learn.  
Преобразование в ONNX-ML:  
- Снижение времени отклика: среда выполнения ONNX Runtime написана на высокооптимизированном C++, инференс модели логистической регрессии через ONNX Runtime происходит в 2–8 раз быстрее, чем стандартный вызов .predict_proba() в Python.
- Кросс-платформенность: модель, обученную на Python, можно запустить внутри банковского бэкенда на Java, C#, Go или C++ без развертывания инфраструктуры Python.
- Безопасность зависимостей: Для инференса на сервере больше не требуются библиотеки scikit-learn, pandas и numpy, нужен только пакет onnxruntime.
Процесс конвертации состоит из четырех шагов:
- Загрузка сохраненного бинарного файла пайплайна Scikit-Learn из формата pickle.
- Определение формата и размерности входных данных. Для модели скоринга фиксируется количество, а размер пакета данных (Batch Size) оставляется динамическим, чтобы сервис мог обрабатывать как одного клиента, так и массив из тысяч клиентов одновременно.
- Преобразование структуры пайплайна (включая StandardScaler и LogisticRegression) в синтаксис ONNX с помощью специализированного конвертера skl2onnx.
- Запись полученного сериализованного графа на диск в виде файла с расширением .onnx.
В коде инференса вместо вызова методов Scikit-Learn инициализируется сессия ONNX Runtime, в которую передаются входные признаки клиентов в виде матрицы чисел с плавающей точкой. На выходе сессия возвращает массив с предсказанными классами и вероятностями.  

# Использование uWSGI + NGINX в production-среде.
Встроенный в Flask сервер, запускаемый через стандартный метод app.run(), является исключительно инструментом для локальной разработки и отладки. Он работает в один поток, не защищен от сетевых перегрузок и не способен стабильно обрабатывать реальный трафик. В промышленной (production) среде для обеспечения отказоустойчивости применяется классический трехслойный контур: Клиент — Web-сервер (NGINX) — WSGI-сервер (uWSGI) — Flask-приложение (ML-код).
*Роль uWSGI (WSGI-сервер приложений):*
Классические веб-серверы, включая NGINX, спроектированы для эффективной отдачи статических файлов и проксирования трафика, но они не умеют напрямую исполнять код, написанный на языке Python. Для решения этой проблемы используется стандарт WSGI (Web Server Gateway Interface) — унифицированный протокол взаимодействия между веб-сервером и Python-фреймворком. Сервер приложений uWSGI выступает в роли связующего звена и управляющего процессами:
- Управление процессами (Master-Worker Architecture): uWSGI запускает один главный (Master) процесс, который управляет пулом изолированных рабочих процессов (Workers), содержащих веса ML-модели в оперативной памяти. Это позволяет обрабатывать запросы на скоринг параллельно в несколько потоков.
- Отказоустойчивость: если в процессе инференса одного из клиентов произойдет критический сбой (например, из-за скрытой аномалии в данных вызовется утечка памяти и рабочий процесс упадет), главный процесс uWSGI мгновенно уничтожит поврежденный воркер и поднимет вместо него чистый новый процесс. Для конечного пользователя этот сбой пройдет незаметно, и сервис продолжит непрерывную работу.
- Эффективное распределение ресурсов: uWSGI оптимально распределяет вычислительную нагрузку по ядрам процессора сервера, минимизируя накладные расходы интерпретатора Python и сокращая время работы модели под высокой нагрузкой.
*Роль NGINX (Reverse Proxy / Обратный прокси-сервер):*
NGINX располагается на внешнем контуре системы и выступает в качестве единой точки входа для всех входящих сетевых запросов от пользователей или других банковских сервисов. Его основные задачи включают:
- Обеспечение безопасности (Security): NGINX скрывает внутреннюю структуру сети, реальные IP-адреса и порты, на которых запущены Python-контейнеры. На уровне NGINX настраиваются SSL/TLS сертификаты для шифрования трафика (HTTPS), а также выставляются ограничения на количество запросов в секунду (Rate Limiting) для защиты от DDoS-атак.
- Балансировка нагрузки (Load Balancing): при масштабировании системы NGINX может распределять входящие запросы между несколькими параллельно запущенными Docker-контейнерами с моделью, обеспечивая равномерную утилизацию мощностей серверов.
- Буферизация медленных клиентов: сетевое соединение у внешних клиентов может быть нестабильным. NGINX берет на себя задачу полностью принять и собрать тяжелый входящий JSON-пакет, удерживая соединение. Только после полной сборки запроса он мгновенно передает его во внутренний контур, не заставляя вычислительные ресурсы ML-модели простаивать в ожидании передачи данных.
